# Documentation templates

Fill these templates in the project's resolved output language. Keep headings and
structure identical across languages; translate prose only. Never translate code,
identifiers, commands, or file paths. File names stay in English kebab-case.

---

## Reference — `reference-<slug>.md`

```markdown
# <Entity name>

<One paragraph: what it is, what it does, when you would use it.>

## API / Interface

<Complete public surface: functions, commands, config options, parameters.
Include types, defaults and constraints, pulled directly from code. Do not
paraphrase loosely.>

## Options / Configuration

<If applicable: every option with its type, default and effect, as a table.>

| Option | Type | Default | Effect |
|---|---|---|---|

## Examples

<2-3 concrete examples that would actually run if copy-pasted. Prefer real
command output or code taken from the tests.>

## Related

<Links to the matching Explanation doc and any related Reference docs.>
```

**Rules:** accuracy over elegance; types/defaults/constraints always; real
examples; no "why" (that is Explanation).

---

## Explanation — `explanation-<slug>.md`

```markdown
# <Concept / design decision>

<Opening paragraph: the problem this design solves, in terms a smart reader who
has not seen the code would understand.>

## The problem

<What goes wrong without this design. Real failure modes, not abstract risks.>

## The approach

<How the design solves the problem. Include an ASCII diagram for anything
architectural.>

## Trade-offs

<What was given up. Every design decision trades something — name it.>

## Alternatives considered

<Only if discoverable from code comments, ADRs or git history: what was tried or
rejected and why. Never invented.>

## Related

<Links to the matching Reference doc.>
```

**Rules:** lead with the problem; ASCII diagrams for architecture; name
trade-offs; link, do not repeat Reference.

## How-to — `howto-<slug>.md` (on request only)

```markdown
# How to <accomplish a specific task>

<One sentence: what you will accomplish and the end result.>

## Prerequisites

<What the reader needs first: versions, installed tools, config state.>

## Steps

1. <Action verb> <specific instruction>

   ```bash
   <exact command>
   ```

   <Expected result, if non-obvious.>

## Verification

<A command, URL or test that confirms it worked.>

## Troubleshooting

<Common failure modes and their fixes, pulled from tests and error handling.>
```

**Rules:** title starts with "How to"; every step actionable; always include
verification; troubleshooting mandatory if the task can fail.

## Tutorial — `tutorial-<slug>.md` (on request only)

```markdown
# <What you will build or learn>

<Opening: what you will build, why it is useful, what you will understand by the
end. Concrete: "You will build a working X that does Y.">

## What you will need

<Prerequisites: tools, versions, prior knowledge.>

## Step 1: <set up the foundation>

<Start from a clean state. Show every command. Explain briefly on first use.>

## Step 2: <first working piece>

<Get to a visible result fast — within the first 3 steps.>

## What you built

<Recap what the reader now has; link to Reference for depth; suggest next steps.>
```

**Rules:** time to first result in under 3 steps; every step produces a visible
change; exact commands, no abstractions; show error + fix inline where a step
commonly fails.
